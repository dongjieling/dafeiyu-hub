## 一、发布门槛（P0，必须修完才能再发版）

### P0-1 重试会过期：约 3 分钟寿命

**现状**

```
启动后 20 秒开始，每 60 秒重试一次，条件 retry_count < 3
→ 三次全部失败后，该记忆永久不再重试，界面上也看不到
```

**问题**

hub 是开机自启的，AstrBot / LivingMemory 往往后启动。
三次重试全打在"LM 未就绪"上 → 3 分钟后这条记忆静默死亡。

**修法**

| # | 改动 |
|---|---|
| 1 | 重试前先探测 `/health`，LM 未就绪时**不消耗重试次数** |
| 2 | 指数退避：1min → 5min → 15min → 1h |
| 3 | 超过 N 次后进"死信"（`status='dead'`），状态页显示条数 |
| 4 | LM 恢复后重置失败计数（避免历史失败永久卡死） |

**验收**

- 停掉 LivingMemory → 写入一条记忆 → 等 5 分钟 → 重启 LM → 该记忆在 3 分钟内被补写
- 状态页能看到"待重试 N 条 / 死信 M 条"

### P0-2 原子补丁只对新写入生效

**实测**

| 指标 | 数值 |
|---|---|
| hub 写入的文档 | 30 条 |
| 其中有原子的 | **2 条**（#118、#119） |
| 历史文档缺原子 | **28 条** |

**问题**

补丁是"从下一条开始生效"，28 条历史记忆仍是扁的：
QQ 侧对桌宠旧记忆的图谱召回为空。

**修法**

| # | 改动 |
|---|---|
| 1 | 写一次性回填脚本：读 `documents` 中 `source=external_api` 且无原子的记录，调用插件原子构建逻辑 |
| 2 | 「立即修复」按钮接上 `reloadPlugin`（现在只改文件，AstrBot 内存里还是旧模块） |
| 3 | 自检从"全文子串匹配"改成"写一条测试记忆 + 数原子" |

**验收**

- 回填后 30 条 hub 文档全部有原子
- 点「立即修复」后无需重启 AstrBot，新写入即带原子

## 二、体验与可靠性（P1）

### P1-1 QQ 同步游标脆弱

**风险**

| 场景 | 后果 |
|---|---|
| 源库被清空重建（id 从 1 开始），游标仍是 2365 | **同步永远静默停止** |
| 游标丢失（换库/恢复备份） | **全量重复导入** |
| 某行 `session_id` 为空 → `continue` | 游标不前进，反复重读同一批 |

**修法**

1. `messages` 加唯一索引 `(session_id, src_id)`（现在没有任何索引）
2. 启动时检测 `max(source.id) < cursor` → 自动重置游标并记录日志
3. 把"上次同步时间 / 游标 / 本次新增"暴露到 `/health`

### P1-2 同步不可观测

| 问题 | 修法 |
|---|---|
| `qq_source_db` 为空时静默返回 0 | 启动时打印"未配置 QQ 同步" |
| 没有新增就不写日志 | 每次同步写一行（含耗时、游标） |
| 参数页没有 `sync_qq` / `qq_source_db` / `write_scope` | 补进参数页 |
| 状态页只有三个灯 | 加"归档"卡片：QQ 条数 / 桌面条数 / 上次同步 |

### P1-3 隐私范围扩大

**现状**：同步了全部会话（含群聊、他人私聊），`archive.db` 明文 1965 条。

**需要决策**（待定）：

- 方案 A：会话白名单（只同步主人私聊 + 指定群）
- 方案 B：全同步 + 文档明确"archive 含他人消息，勿外发"
- 方案 C：全同步 + 本地加密
