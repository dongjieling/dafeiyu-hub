# 记忆链路事故报告与重构建议

> 范围：2026-11-23 至 2026-11-25，覆盖中转站 v0.1 → v0.4.7
> 结论先行：**同一功能反复出问题，不是运气差，是架构缺三样东西——可观测、单一真相、端到端契约。建议做结构性重构（不是重写）。**

---

## 一、摘要

| 指标 | 数值 |
|---|---|
| 记忆链路相关发布 | 9 个版本（v0.3.1 → v0.4.7） |
| 确认的事故 | 10 起 |
| 其中"静默失败"类 | 5 起（占一半） |
| 平均修复时间 | 当天（最短 20 分钟，最长 8 小时） |
| 用户可感知故障 | 4 次「QQ 接不到桌宠说的话」 |
| 误判次数 | 3 次（都发生在最后一次排查中） |

**一句话**：这条链路有 4 个独立存储（hub 归档库、LM 文档、LM 原子/图谱、插件配置），
任何一处静默失败，最终表现都是同一句「她不知道」。

## 三、共性分析：四类根因

### A. 静默失败（5 起，最致命）

| 事故 | 失败表现 |
|---|---|
| #3 写回失败 | 只打一行日志 |
| #4 补丁丢失 | 没有任何提示 |
| #5 重试耗尽 | 记录进死信但没人看 |
| #8 `_enc_field` 未定义 | 只在"有新消息"时触发 |
| #10 提炼解析失败 | 只打一行 `Expecting value` |

**共同点**：失败后系统继续跑，日志里有一行看不懂的错，没有任何汇总。
所以每次都是"用户先发现，我再回查"。

### B. 分层混淆（3 起）

同一条链路有 5 层：

```
① 采集（QQ/桌宠消息）
② 提炼（LLM 判断记不记）
③ 写入（LM 文档 → 原子 → 图谱）
④ 检索（向量 + BM25 + 图谱扩展）
⑤ 注入（拼进提示词）
```

任何一层坏掉，用户看到的都是"她不知道"。
排查时我三次跳到第 ④ 层（检索词、类别词），实际问题在第 ③ 层（根本没写）。

### C. 配置与版本漂移（3 起）

| 事故 | 漂移点 |
|---|---|
| #1 归档只有桌面 | 代码写死 source |
| #4 补丁丢失 | 第三方插件升级 |
| #8 建表缺列 | 新装库 schema 与代码不同步 |

根子在于：**同一份语义散落在 4 个地方**（hub 配置、插件配置、插件源码补丁、数据库 schema）。

### D. 检索质量（2 起）

- `topics` 用 `content[:12]`（等于没标注）
- 缺类别词，泛问没有可匹配 token

这类问题不影响"有没有"，只影响"搜不搜得到"，更难发现。

## 四、代码层面的具体问题

| 位置 | 问题 | 风险 |
|---|---|---|
| `hub.py` | 路由是 `if path == ...` 硬编码 | 加功能容易漏（v0.4.7 自检路由就漏了一次 404） |
| `memory.py` | 召回/提炼/写回/归档混在一个文件（360 行） | 改动互相影响 |
| `sync.py` | 游标单调递增假设 | 源库重建后永久停更 |
| `selftest.py` | 事后补的，不是流程一部分 | 只能是"事后体检"，不能防 |
| 插件补丁 | 直接改第三方源码 | 升级即失效 |
| 配置 | hub 配置与插件配置两处 | 两边不一致时无从判断以谁为准 |
| 日志 | 只有文本行，无结构化字段 | 无法统计"召回成功率" |

## 五、要不要重构

### 结论：要，但**不是重写**

现有 `sidecar` 的模块划分（config/upstream/memory/knowledge/prompt/persona/sync/retry）
本身是合理的，问题不在分层，而在这三层缺失：

1. **没有统一管线**：写入走 4 条不同代码路径（归档、提炼、写回、重试）
2. **没有可观测指标**：只有日志文本，没有"本轮写入成功/失败/耗时/层"
3. **没有端到端契约测试**：自检是事后加的，不是每次改动自动跑

所以重构方向是**把隐式流程显式化**，而不是推倒重来。

### 目标架构

```
MemoryPipeline
├── stage: capture   （收到消息）
├── stage: extract   （LLM 提炼，带解析容错 + 重试）
├── stage: persist   （写 LM，含 idempotency + 原子补丁检查）
├── stage: index     （确认可检索，带超时）
└── stage: retrieve  （召回，带作用域过滤 / 去重 / 重要度）

每一 stage 统一返回：
{ ok, latency_ms, error, retry, trace_id }
→ 汇总到 /health 与 状态页
```

特性：

| 特性 | 解决的事故 |
|---|---|
| 每 stage 强制 ok/error | A 类静默失败 |
| 状态页显示"最后一轮卡在哪" | B 类分层混淆 |
| 配置单一真相 | C 类漂移 |
| 检索质量层（去重/重要度/域过滤） | D 类质量 |
| 写入后立刻验证可检索 | #10 类"写没写进去" |

### 分三期

| 期 | 内容 | 工作量 | 验收 |
|---|---|---|---|
| **一期：可观测** | Pipeline 骨架 + 每 stage 指标 + 状态页 | 1 天 | 任意一次失败能在状态页指出是哪层 |
| **二期：统一写入** | 归档/提炼/写回/重试收敛到一条路径 + 写入后验证 | 2 天 | 代码里只有一处 `write_memory()` |
| **三期：质量与后端** | 去重、重要度重做、作用域过滤、后端抽象（MCP） | 3–4 天 | 泛问命中率、去重率、可换后端 |

### 明确不做

- 不换框架（Electron + Python 够用）
- 不重写检索（LM 的混合检索比自研强）
- 不做多用户/权限（个人使用）

---

## 六、如果只做一件事

**做一期：可观测。**

理由：这次排查花了一整天，其中至少 6 小时是浪费在"猜哪一层坏了"。
如果状态页直接告诉我「最后一轮：写入失败，JSON 解析错误」，十分钟就能定位。

事故可以继续修，但**必须先让故障自己说话**。
