## v0.1.0（2026-11-23）

**第一个可用版本。** 从"想让桌宠也记得我"到能跑通的双向记忆。

### 起点

桌宠（AIRI）和 QQ 机器人（AstrBot）各自记各自的事：

| 端 | 记忆存哪 | 问题 |
|---|---|---|
| QQ | LivingMemory（197 条原子记忆） | 桌宠看不到 |
| 桌宠 | 自己的会话（退出即清空） | QQ 看不到 |

目标：**一个"她"，两个入口，一套记忆。**

### 关键调研：LivingMemory 到底能做什么

只读调查了插件 v2.14.2，结论：

| 发现 | 意义 |
|---|---|
| 有官方文档的外部记忆 API | 不用重写记忆引擎 |
| 端口 7801，路径 `/page/external` | 可被本地程序调用 |
| 写接口 `POST /memories`，支持幂等键 | 可安全重试 |
| 召回接口 `POST /recall` | 可做提示词注入 |
| 附带 MCP bridge | 另一条可选路径 |

**最重要的限制**：

```python
importance_value = payload.get("importance", 0.5)   # 传多少存多少
```

外部写入是"哑存储"——**它不做内容判断**。
"这句话值不值得记"必须由调用方（本项目）判断。

### 架构决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 记忆引擎 | 复用 LivingMemory | 它有去重、向量化、图谱、衰减，重写要几周还容易做差 |
| 网关位置 | 只放在桌宠链路 | QQ 侧 LM 已经覆盖，加一跳只增故障点 |
| 记忆写入 | 只写 LM 一处 | 两套并行写入会冲突 |
| 归档 | 本地 SQLite 存原文 | 可回溯、可重建，但不参与检索 |
| 判断逻辑 | 规则粗筛 + AI 精判 | 规则省钱，AI 保质量 |
| 界面外壳 | Electron | 用户要求"像桌面软件"，且打包分发成熟 |

**明确不做**：

- ❌ 解析桌宠的 IndexedDB（二进制，升级即坏）
- ❌ 直接写 LivingMemory 数据库（绕过嵌入与图谱）
- ❌ 复制 LivingMemory 代码（AGPL 会传染）

### 实现过程

```
Electron 外壳（窗口/托盘/启停）
   +
Python sidecar（代理 + 人格 + 记忆）
   +
SQLite 归档库
```

**后端坚持用 Python**：读写 SQLite、调 HTTP、调模型都用标准库就够了，零第三方依赖。
Electron 只负责界面与生命周期，不重复实现业务逻辑。

### 踩过的坑

| # | 问题 | 根因 | 解决 |
|---|---|---|---|
| 1 | `npm install` EPERM | 缓存目录在受限路径 | `--cache` 指到工作区 |
| 2 | Electron 二进制没下载 | postinstall 被跳过 | 手动跑 `install.js` |
| 3 | bat 双击闪退 | **LF 换行**，cmd 把 `cd /d` 拆断 | CRLF + ASCII |
| 4 | 启动弹错误框 | 手写的 base64 图标是坏 PNG | 用 Pillow 生成真图标 |
| 5 | sidecar 不启动 | 路径按不同布局解析失败 | 三个候选路径依次尝试 |
| 6 | 流式等 61 秒超时 | 流式结束不关连接，客户端等 EOF | `Connection: close` |
| 7 | 日志 62% 是健康检查 | 每次 `/health` 都记日志 | 过滤 + 探测缓存 |
| 8 | 打包后数据写不进去 | 数据写在只读的 resources 目录 | `HUB_DATA_DIR` 环境变量 |
| 9 | 界面改端口无效 | 两处配置各自为政 | 主进程通过环境变量下发 |
| 10 | 写入了「她关心他」 | 提示词要求第三人称，模型跑偏 | 过滤「她/我/你」开头 |

### 最关键的发现：作用域

LivingMemory 按 `scope` 隔离记忆。实测：

| 召回 scope | 能看到桌宠写的吗 |
|---|---|
| `airi:desktop` | ✅ |
| `一号:FriendMessage:<QQ>` | ❌ |
| 不传 | ✅ |

第一版写入用了 `airi:desktop`，结果 **QQ 里完全问不出来**。

修正：写入时用 QQ 私聊域（`write_scope`），召回时不传 scope。
这样两边都能看到。

### 实测效果

**召回**（桌宠答出 QQ 里的记忆）：

```
问：你还记得我喜欢吃什么吗
答：（尾巴晃了晃）鸡丝面嘛，2026-11-23中午那顿。
```

**写回**（QQ 答出桌宠聊的内容）：

```
桌宠：我下周要去杭州出差三天
→ 后台提炼：「他下周要去杭州出差三天，周三到周五」(重要性 0.6)
→ QQ 里问「我下周去哪出差」→ 答出杭州
```

## v0.1.1（2026-11-24）

**主题：让召回真的可用。** 前一天 v0.1.0 能跑通，但实际使用时经常"她不知道"。

### 三个实测发现

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 桌宠问什么都答不出来 | AIRI 在消息前塞了 `[时间戳]` + `[Context]` + `<\|ACT\|>` 标记，检索语义被污染 | 加 `clean_query` 剥离三轮污染 |
| 2 | 记忆里明明有，就是唤不回 | 新写入的记忆要 30–60 秒建完向量索引 | 无代码修法，属于机制；文档写明「等一分钟」 |
| 3 | 之前说不知道，之后一直不知道 | 长历史锚定：模型延续自己之前的结论 | 记忆移到最后一问之前 + 显式要求「不要因为之前说过不知道就继续不知道」 |

### 其他调整

| 项 | 之前 | 现在 |
|---|---|---|
| `recall_k` | 5 | 8（细节不易被截断） |
| 记忆注入位置 | 系统提示开头 | 最后一条用户消息之前 |
| 注入措辞 | 「你记得关于他的事」 | 「你现在想起来了的关于他的事」 |
| AstrBot 总结阈值 | 10 轮 | 2 轮（QQ 侧同步从十几分钟降到 1 分钟） |

### 验证方式

模拟"前几轮一直说不知道"的历史，再问同样的问题：

```
你：我跑了多少米你知道吗
她：这个真不知道诶
你：我体测跑多少米
她：一千米！想起来了吧（甩尾巴）
```

### 经验

- **能回答 ≠ 记忆打通**：要区分"没写入 / 没召回 / 召回了但没用上 / 被历史带跑"四种情况
- 日志里必须能看见**实际召回的内容**，否则只能猜；本项目为此加了「召回查询」「召回详情」两行
- 提示词的位置（在长上下文的哪里）比提示词的内容更容易被忽略

### 参数页踩的坑

第一版字段路径是"看着像"写的，实测发现 4 个是错的：

| 字段 | 错误路径 | 实际路径 |
|---|---|---|
| 记忆原子开关 | `graph_memory_atom_enabled` | `graph_memory.atom_enabled` |
| 主动开关 | `enable_auto_trigger` | `friend_settings.auto_trigger_settings.enable_auto_trigger` |
| 触发间隔 | `auto_trigger_after_minutes` | 同上层级 |
| 未回复上限 | `max_unanswered` | `friend_settings.schedule_settings.max_unanswered_times` |

**危害**：写入时 `setByPath` 会自动创建中间对象，等于往配置里塞垃圾键。

**修法**：
1. 逐字段核对配置文件里的真实路径
2. 写入前检查路径已存在，不存在就拒绝并报错

```js
if (getByPath(cfg, dotPath) === undefined) {
  return { ok: false, error: `配置里没有 ${dotPath}` };
}
```

### 配置位置的架构修正

v0.2 的打包版把 `config.json` 打在包里（`resources/sidecar/`），导致：

- 用户改不了配置（资源目录）
- 发布版跑起来连不上记忆库（密钥是空的）

**修正**：配置统一放数据目录

```
首次运行：包内模板 → 复制到 %APPDATA%\dafeiyu-hub\config.json
之后：只读写数据目录那份
```

兼容规则：环境变量 > 数据目录 > 包内模板 > 默认值。

## v0.3.1（2026-11-25）

**主题：把三个硬性问题一次修掉。**

### 1. 归档只记桌面侧 → 补 QQ 同步

之前 `archive.db` 只有桌宠的对话（代码里写死 `source='airi'`），
QQ 侧聊的全都不在归档里。

**修法**：新增后台同步任务，从 AstrBot 的原始对话库增量导入：

```
%USERPROFILE%\.astrbot\data\plugin_data\astrbot_plugin_livingmemory\conversations.db
        ↓ 按 id 游标增量
    archive.db（source='qq'）
```

实测：一次追平 1965 条 QQ 消息 + 122 条桌面消息 = 2087 条。

细节：

- 游标存在归档库的 `kv` 表（`qq_cursor`）
- 单次最多追 5000 条，分 500 一批
- 会话按 `session_id` 归并，元数据保留发送者与群号

### 2. 外部写入没有原子层 → 给插件打补丁

`add_memory` 只有在 `metadata["summary_schema_version"] == "v2"` 且带
`key_facts` 时才生成原子，而外部 API 构造 metadata 时没带这个字段。

**修法**：在插件 `core/external_api.py` 补一行：

```python
metadata["summary_schema_version"] = "v2"
```

实测：写入「他明天下午三点去修自行车 + 链条断了」，生成两条原子
（`planned` / `unknown`），挂在文档 118 下。

⚠️ 这是本地补丁，插件升级会被覆盖；升级后需重新打。

### 3. 写回失败没有重试 → 后台重试

之前失败只记日志，那条记忆就丢了。

**修法**：

- `extractions` 表加 `retry_count` 列
- 后台线程每 60 秒扫 `status='failed' AND retry_count < 3`
- 用同一幂等键重发，成功后改 `written`

实测：插入一条假失败记录，重试一次即成功。

### 顺带修的

| 项 | 说明 |
|---|---|
| 写回超时 15s → 45s | 生成原子要算 embedding，15 秒不够 |
| 版本号统一 | sidecar 版本由宿主 `HUB_VERSION` 传入 |
| 归档清理 | `retention_days`，0 = 永久 |
| 日志脱敏 | `logging.log_content=false` |

## v0.4.0（2026-11-25）

**主题：把 v0.3.2 评审提出的 P0 全部清掉。**

评审结论是"三个新功能都停在'做完了'，没到'做稳了'"。这版专门补"最后一公里"。

### P0-1 重试不再过期

之前：3 次 × 60 秒 = 3 分钟寿命，LM 没起来就全打空，然后永久不重试。

现在：

| 改动 | 说明 |
|---|---|
| 健康门控 | LM 未就绪时**不消耗**重试次数 |
| 指数退避 | 1min → 5min → 15min → 1h |
| 死信 | 第 5 次失败标记 `dead`，状态页可见 |
| 统计 | `/health` 暴露 `pending_retry` / `dead_letters` |

实测（隔离库）：

```
LM 未就绪 → retry_count 不变（未消耗）
失败一次 → next_retry_at = +60s
第 5 次失败 → status=dead
```

### P0-2 原子回填完成

v0.3.2 的补丁只对新写入生效，28 条历史记忆仍是"扁的"。

调用插件自己的 `classify_atoms` + `AtomStore.insert_many` 回填。

结果：**30/30 hub 文档都有原子**，原子总数 488。

另外两项：

- 「立即修复」按钮现在会**顺带重载插件**（以前只改文件，AstrBot 内存里还是旧模块）
- 自检从"全文子串匹配"改成"锚定 `key_facts` 赋值行 + 后 5 行内找标记"，避免误判

### P0-3 发布卫生

## v0.4.1（2026-11-25）

**主题：归档库加密。**

### 为什么做

归档同步把 QQ 侧全部会话都拷了进来（群聊、他人私聊），
`archive.db` 是明文 SQLite——文件被拷走就等于聊天记录泄露。

### 做法

| 项 | 实现 |
|---|---|
| 算法 | AES-256-GCM（`cryptography`） |
| 密钥 | 32 字节随机，Windows DPAPI 绑定账户后落盘 |
| 范围 | 消息内容、消息元数据、提炼文本 |
| 兼容 | 旧明文原样读取，迁移脚本负责加密历史 |
| 开关 | `archive.encrypt`（默认 true） |

密文格式 `enc:v1:<base64(nonce||ciphertext)>`，二次加密幂等。

### 迁移

`encrypt_archive.py`：

```
messages:      2273 条 → 已加密
extractions:     25 条 → 已加密
抽样: enc:v1:MlczvLEYabAgHak93HMsjbLdGN1R4IAm10k5uxmYCls...
```

### 一个必须记住的坑

**加密字段不能直接发给下游。**

第一次测试时，重试任务把 `extractions.content`（已加密）直接 POST 给了
LivingMemory，导致记忆库里出现一条 `enc:v1:...` 的密文记忆。

修法：`retry.py` 在发请求前先 `crypto.decrypt()`；日志里也只打明文前缀。

已清理：删除该密文文档、原子、图谱节点，并 rebuild FTS。

### 局限（写进文档了）

| 能防 | 不能防 |
|---|---|
| 文件被拷走 | 同账户程序读取 |
| 硬盘送修 | 内存转储 |
| 网盘备份泄露 | 木马 |

DPAPI 绑定账户：换账户后旧库解不开，需要先导出密钥。

## v0.4.2（2026-11-25）

**主题：修 v0.4.1 评审的 4 个 P0。**

评审原话：*"加密这一刀切下去时，把 QQ 同步的线剪断了。"*

### 修了什么

## v0.4.3（2026-11-25）

**主题：桌宠说的话，QQ 侧问不出来。**

### 现象

桌面告诉桌宠「我今天中午又吃的便利店」，QQ 问「我今天中午吃的啥」，
回答是「桌宠那边说的，我这边接不到」。

### 排查

记忆库是通的：

- 召回 `[我今天中午吃的啥]` 有结果
- 归档里也有原文

问题在**写进去的内容**：

```
桌面说：我再告诉你我今天又吃的便利店
写回：  他经常吃便利店凑合，饮食不太规律
```

具体时间点被概括掉了。

### 两个原因

| # | 原因 |
|---|---|
| 1 | AIRI 消息带 `[2026-11-25 13:29]`、`[Context]` 块、`<|ACT|>` 标记，原样丢给提炼模型 |
| 2 | 提示词只要求"第三人称、40 字内"，没要求保留具体事件 |

1. 新增 `clean_for_extract()`：去掉时间戳、Context 块、ACT/DELAY 标记、`- system:` 行
2. `hub` 在交给记忆任务前先清洗（存档仍保留原文）
3. 提示词加硬约束：

```
具体事件必须单独成条，不能被习惯概括吞掉。
他说"我今天中午又吃的便利店" → 记 "他2026-11-25中午又吃了便利店"
不要写成 "他经常吃便利店"
```

4. 每轮最多条数 2 → 3

```
输入：我今天中午吃的牛肉面，加了两个蛋
写入：他今天中午吃了牛肉面，加了两个蛋
召回：问"我今天中午吃的啥" → 命中该条
原子：#651，session=一号:FriendMessage:123456789
```

`重要度 0.4` 仍偏低——提示词说"越稳定越重要"，导致具体事件分数低。
这是下一步"重要性通胀"要一起处理的问题，先记录。

## v0.4.4（2026-11-25）

**主题：记忆在，但换个说法就搜不到。**

### 现象

```
桌面 13:42  我今天晚上还要去准备辩论赛
写回 13:42  他今晚要去准备辩论赛（importance 0.6）

QQ   13:43  你知道我晚上干嘛  →  这个我真不知道
QQ   13:44  你不知道吗？好好想想  →  真不知道
```

看起来是"没同步"，其实是**检索没命中**。

### 排查方法

用同一批换说法直接打记忆库：

| 问法 | 命中「辩论赛」 |
|---|---|
| `今晚要做什么` | ✅ 第 1 |
| `辩论赛` | ✅ 第 1 |
| `你知道我晚上干嘛` | ❌ 前五都没有 |
| `我晚上干嘛` | ❌ 前五都没有 |

### 原因

写回时 `topics` 用的是 `content[:12]`——**内容前 12 个字**，几乎等于没做检索标注。
中文口语换说法（"晚上干嘛" vs "今晚要做什么"）就匹配不上。

### 修复

让提炼模型额外输出 2–3 个检索关键词：

```json
{"content": "他今晚要去准备辩论赛", "importance": 0.6,
 "topics": ["晚上安排", "辩论赛", "今晚"]}
```

写回时把这些关键词一起发给记忆库。

### 验证

新写一条「下周三去医院做胃镜」，然后换四种说法问：

| 问法 | 修复前 | 修复后 |
|---|---|---|
| 我下周要干嘛 | 未命中 | 第 2 |
| 我周三有什么事 | 未命中 | 第 1 |
| 你知道我哪天要去医院吗 | 未命中 | 第 4 |
| 下周三 | 未命中 | 第 2 |

「我最近身体怎么样」仍未命中——这类泛问需要靠图谱写回，属于下一步。

### 教训

"同步失败"和"检索失败"表现一样（都是答不上来），
排查时要**直接用同一句话打记忆库**，而不是看日志有没有写回。

## v0.4.6（2026-11-25）

**主题：提炼静默失败。**

### 这是"QQ 接不到"的真正原因

前面三次（v0.4.3 / 0.4.4 / 0.4.5）都在调"提炼写什么、检索怎么匹配"。
但那些都不重要——因为那几分钟里**根本没写进记忆库**：

```
15:47:50 提炼失败: Expecting value: line 1 column 1 (char 0)
15:49:42 提炼失败
15:50:44 提炼失败
15:51:16 提炼失败
```

用户 15:47 说的「今晚有职业生涯规划课程」，落在失败窗口里，
记忆库里没有这条 → QQ 怎么问都问不出来。

### 三个原因

| # | 原因 | 后果 |
|---|---|---|
| 1 | 加了 topics 后输出变长，`max_tokens=300` 容易截断 | JSON 不完整 |
| 2 | 解析失败直接 `return []`，只留一行看不懂的日志 | 静默丢数据 |
| 3 | AIRI 把「每次回复都要以 ACT token 开头…」拼进用户消息 | 模型被带偏 |

### 修复

```python
# 1. 给够 token
'max_tokens': 700

# 2. 解析容错：围栏 / 散文 / 截断
parse_extract_json(raw)   # 抽出纯函数，可单测

# 3. 清洗时切掉 ACT 指令段
s = re.split(r'每次回复都要以\s*ACT', s)[0]
```

截断修复的做法：从第一个 `[` 开始，依次尝试原串、补 `]`、截到最后一个 `}` 再补 `]`。

### 验证

修复前连续 4 次失败；修复后连发 3 条，3 条全部写回。

补写漏掉的课程事实后，QQ 侧问法命中：

| 问法 | 结果 |
|---|---|
| 我今晚有什么课 | 命中 |
| 职业生涯规划课程 | 第 1 |
| 我最近压力大吗 | 第 1 |

### 新增测试（25 个用例）

`ExtractParseTest`：

- 纯 JSON
- 代码围栏
- 空内容
- **截断的 JSON**
- 散文夹带数组
- ACT 指令清洗

### 教训

前三次都在错误的层找原因。真正该做的是**先看日志有没有报错**，
而不是假设"写进去了但搜不到"。

这也是为什么日志里那句 `提炼失败: Expecting value...` 应该更早被注意到——
它是唯一能直接指出"没写进去"的信号。

## v0.4.7（2026-11-25）

**主题：连通性自检。**

### 为什么做

排查"QQ 接不到"花了一整天，中间反复在"写入 / 索引 / 检索 / 模型行为"四层里猜。
如果一开始就有个自检按钮，一层层跑一遍，能省掉大半时间。

### 自检做五步

| 步骤 | 方法 |
|---|---|
| 配置完整 | 检查 `lm_key` / `persona_db` / `write_scope` |
| 记忆库在线 | `GET /health` |
| 写入测试记忆 | 写一条 `【自检】SELFTEST-xxxx` |
| 检索回测试记忆 | 轮询 `/recall`，最多 25 秒 |
| 知识库检索 | 启用时取一段资料 |

返回每步的 `ok / detail / ms`，界面按行显示。

### 清理

因为插件的外部 API 不支持删除（`DELETE` 返回 405），
清理只能直接操作 SQLite：

```
documents → 删带【自检】的
memory_atoms → 删对应原子
graph_entries / graph_entry_nodes → 删对应条目
graph_nodes → 删孤立节点
FTS → rebuild
```

### 实测

```
OK 配置完整 (0ms)
OK 记忆库在线 (38ms)
OK 写入测试记忆 (638ms)
OK 检索回测试记忆 (153ms)
OK 知识库检索 (447ms)
→ 全部通过

清理: 文档 3 条、原子 2 个、节点 5 个 → 剩余 0
```

### 测试

27 个用例通过，新增 2 个清理用例：
只删带标记的、无标记时不动数据。

### 一个设计取舍

清理是"删库"而不是"调接口"，风险更高。
所以：只匹配固定标记 `【自检】`、清理前建议备份、日志记录删除数量。

## 设计取舍备忘

### 为什么不用向量库自己做

LivingMemory 已经实现了去重、多路召回、图谱扩展。
自己再造一个只会更差，而且数据会分裂成两份。

### 为什么原文要另存一份

记忆库只存"要点"，原始对话会丢。
归档库是保险：记忆库坏了能重建，也能回答"我当时到底怎么说的"。

### 为什么每轮只提炼 0-2 条

一条消息拆成五条碎片会污染检索。
宁可少记，让重要性衰减机制去淘汰，也不要塞满噪音。

### 为什么不给 AI 完全自由

判断"值不值得记"交给模型，但有三道闸：

1. 规则粗筛（长度、重复）
2. AI 精判（重要性门槛）
3. 写入去重（相似度过高跳过）

纯靠模型判断会记下大量寒暄。
