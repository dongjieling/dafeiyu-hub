## v0.1.0（2026-11-23）

**第一个可用版本。** 从"想让桌宠也记得我"到能跑通的双向记忆。

### 起点

桌宠（AIRI）和 QQ 机器人（AstrBot）各自记各自的事：

| 端 | 记忆存哪 | 问题 |
|---|---|---|
| QQ | LivingMemory（197 条原子记忆） | 桌宠看不到 |
| 桌宠 | 自己的会话（退出即清空） | QQ 看不到 |

目标：**一个"她"，两个入口，一套记忆。**

### 关键调研：LivingMemory 到底能做什么

只读调查了插件 v2.14.2，结论：

| 发现 | 意义 |
|---|---|
| 有官方文档的外部记忆 API | 不用重写记忆引擎 |
| 端口 7801，路径 `/page/external` | 可被本地程序调用 |
| 写接口 `POST /memories`，支持幂等键 | 可安全重试 |
| 召回接口 `POST /recall` | 可做提示词注入 |
| 附带 MCP bridge | 另一条可选路径 |

**最重要的限制**：

```python
importance_value = payload.get("importance", 0.5)   # 传多少存多少
```

外部写入是"哑存储"——**它不做内容判断**。
"这句话值不值得记"必须由调用方（本项目）判断。

### 架构决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 记忆引擎 | 复用 LivingMemory | 它有去重、向量化、图谱、衰减，重写要几周还容易做差 |
| 网关位置 | 只放在桌宠链路 | QQ 侧 LM 已经覆盖，加一跳只增故障点 |
| 记忆写入 | 只写 LM 一处 | 两套并行写入会冲突 |
| 归档 | 本地 SQLite 存原文 | 可回溯、可重建，但不参与检索 |
| 判断逻辑 | 规则粗筛 + AI 精判 | 规则省钱，AI 保质量 |
| 界面外壳 | Electron | 用户要求"像桌面软件"，且打包分发成熟 |

**明确不做**：

- ❌ 解析桌宠的 IndexedDB（二进制，升级即坏）
- ❌ 直接写 LivingMemory 数据库（绕过嵌入与图谱）
- ❌ 复制 LivingMemory 代码（AGPL 会传染）

### 实现过程

```
Electron 外壳（窗口/托盘/启停）
   +
Python sidecar（代理 + 人格 + 记忆）
   +
SQLite 归档库
```

**后端坚持用 Python**：读写 SQLite、调 HTTP、调模型都用标准库就够了，零第三方依赖。
Electron 只负责界面与生命周期，不重复实现业务逻辑。

### 踩过的坑

| # | 问题 | 根因 | 解决 |
|---|---|---|---|
| 1 | `npm install` EPERM | 缓存目录在受限路径 | `--cache` 指到工作区 |
| 2 | Electron 二进制没下载 | postinstall 被跳过 | 手动跑 `install.js` |
| 3 | bat 双击闪退 | **LF 换行**，cmd 把 `cd /d` 拆断 | CRLF + ASCII |
| 4 | 启动弹错误框 | 手写的 base64 图标是坏 PNG | 用 Pillow 生成真图标 |
| 5 | sidecar 不启动 | 路径按不同布局解析失败 | 三个候选路径依次尝试 |
| 6 | 流式等 61 秒超时 | 流式结束不关连接，客户端等 EOF | `Connection: close` |
| 7 | 日志 62% 是健康检查 | 每次 `/health` 都记日志 | 过滤 + 探测缓存 |
| 8 | 打包后数据写不进去 | 数据写在只读的 resources 目录 | `HUB_DATA_DIR` 环境变量 |
| 9 | 界面改端口无效 | 两处配置各自为政 | 主进程通过环境变量下发 |
| 10 | 写入了「她关心他」 | 提示词要求第三人称，模型跑偏 | 过滤「她/我/你」开头 |

### 最关键的发现：作用域

LivingMemory 按 `scope` 隔离记忆。实测：

| 召回 scope | 能看到桌宠写的吗 |
|---|---|
| `airi:desktop` | ✅ |
| `一号:FriendMessage:<QQ>` | ❌ |
| 不传 | ✅ |

第一版写入用了 `airi:desktop`，结果 **QQ 里完全问不出来**。

修正：写入时用 QQ 私聊域（`write_scope`），召回时不传 scope。
这样两边都能看到。

### 实测效果

**召回**（桌宠答出 QQ 里的记忆）：

```
问：你还记得我喜欢吃什么吗
答：（尾巴晃了晃）鸡丝面嘛，2026-11-23中午那顿。
```

**写回**（QQ 答出桌宠聊的内容）：

```
桌宠：我下周要去杭州出差三天
→ 后台提炼：「他下周要去杭州出差三天，周三到周五」(重要性 0.6)
→ QQ 里问「我下周去哪出差」→ 答出杭州
```

## v0.1.1（2026-11-24）

**主题：让召回真的可用。** 前一天 v0.1.0 能跑通，但实际使用时经常"她不知道"。

### 三个实测发现

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 桌宠问什么都答不出来 | AIRI 在消息前塞了 `[时间戳]` + `[Context]` + `<\|ACT\|>` 标记，检索语义被污染 | 加 `clean_query` 剥离三轮污染 |
| 2 | 记忆里明明有，就是唤不回 | 新写入的记忆要 30–60 秒建完向量索引 | 无代码修法，属于机制；文档写明「等一分钟」 |
| 3 | 之前说不知道，之后一直不知道 | 长历史锚定：模型延续自己之前的结论 | 记忆移到最后一问之前 + 显式要求「不要因为之前说过不知道就继续不知道」 |

### 其他调整

| 项 | 之前 | 现在 |
|---|---|---|
| `recall_k` | 5 | 8（细节不易被截断） |
| 记忆注入位置 | 系统提示开头 | 最后一条用户消息之前 |
| 注入措辞 | 「你记得关于他的事」 | 「你现在想起来了的关于他的事」 |
| AstrBot 总结阈值 | 10 轮 | 2 轮（QQ 侧同步从十几分钟降到 1 分钟） |

### 验证方式

模拟"前几轮一直说不知道"的历史，再问同样的问题：

```
你：我跑了多少米你知道吗
她：这个真不知道诶
你：我体测跑多少米
她：一千米！想起来了吧（甩尾巴）
```

### 经验

- **能回答 ≠ 记忆打通**：要区分"没写入 / 没召回 / 召回了但没用上 / 被历史带跑"四种情况
- 日志里必须能看见**实际召回的内容**，否则只能猜；本项目为此加了「召回查询」「召回详情」两行
- 提示词的位置（在长上下文的哪里）比提示词的内容更容易被忽略

## v0.2.0（2026-11-24）

**主题：把能跑的代码整理成好维护的代码。**

v0.1.1 修完召回问题后，单文件 `hub.py` 已经涨到 700 行，职责混在一起，
没有测试，配置分散在三处。这次做结构化重构，**不重写**。

### 模块拆分

```
src/sidecar/
├── hub.py        入口：HTTP 路由 + 上游转发（约 230 行）
├── config.py     配置唯一来源（默认值 + config.json + 环境变量）
├── persona.py    人格读取（带缓存）
├── upstream.py   上游 Key 读取 + 消息清洗
├── memory.py     召回 / 提炼 / 写回 / 归档
├── knowledge.py  知识库检索
├── prompt.py     提示词组装（并行取上下文）
├── util.py       日志（5 MB 轮转）、JWT 签名
└── tests/        15 个单元测试
```

### 三项实质改进

| 改进 | 之前 | 现在 |
|---|---|---|
| **配置来源** | app 配置、sidecar 配置、环境变量三处 | 统一 `config.py`，宿主只传 `HUB_PORT` / `HUB_DATA_DIR` |
| **进程守护** | sidecar 崩了要手动点启动 | 3 秒后自动重启，最多 5 次，稳定 60 秒后重置计数 |
| **检索串行** | 记忆 → 知识库依次查 | 两个线程并行，省约 1 秒 |

### 测试

15 个用例，覆盖最容易回归的三块：

- `clean_query`：时间戳 / `[Context]` / `<|ACT|>` 三层污染
- `build_recall_query`：短消息时拼上下文、多段内容解析
- 提示词组装：人格在最前、记忆插在最后一问之前、原 system 合并

```bash
python -m unittest discover -s tests -v
```

### 日志

- 加 5 MB 轮转（`hub.log` → `hub.log.1`）
- 健康检查与模型列表不再写日志
- 新增「召回查询」「召回详情」「知识库命中详情」三行，排障时一眼看到实际内容

### 验证结果

| 项 | 结果 |
|---|---|
| 单元测试 | 15/15 通过 |
| 人格注入 | 1853 字 |
| 记忆召回 | 答出「体测 1000 米」 |
| 知识库 | 答出「阿米娅是罗德岛公开领袖」 |
| 流式 | 正常 |
| 守护 | 手动杀进程后 3 秒自动恢复 |
| 打包 | 105.2 MB，功能一致 |

## 设计取舍备忘

### 为什么不用向量库自己做

LivingMemory 已经实现了去重、多路召回、图谱扩展。
自己再造一个只会更差，而且数据会分裂成两份。

### 为什么原文要另存一份

记忆库只存"要点"，原始对话会丢。
归档库是保险：记忆库坏了能重建，也能回答"我当时到底怎么说的"。

### 为什么每轮只提炼 0-2 条

一条消息拆成五条碎片会污染检索。
宁可少记，让重要性衰减机制去淘汰，也不要塞满噪音。

### 为什么不给 AI 完全自由

判断"值不值得记"交给模型，但有三道闸：

1. 规则粗筛（长度、重复）
2. AI 精判（重要性门槛）
3. 写入去重（相似度过高跳过）

纯靠模型判断会记下大量寒暄。
