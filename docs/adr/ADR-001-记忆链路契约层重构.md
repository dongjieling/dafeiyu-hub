# ADR-001：记忆链路契约层重构

- 状态：**已接受（含两轮修订），排入 v1.0.0**（2026-11-25）
- 目标版本：**v1.0.0（大版本）**
- 施工状态：**未开工**（规划完成，等待启动）
- 决策人：项目维护者
- 相关文档：[记忆链路事故报告](记忆链路事故报告.md)、[待修复清单](待修复清单.md)

---

## 背景

中转站的记忆链路在 24 小时内出了 10 起事故，5 起属于"静默失败"：

```
提炼解析失败  → 只打一行日志 → 记忆没写进去 → 用户以为"她记不住"
插件补丁丢失  → 没有任何提示 → 原子不再生成 → 召回悄悄变差
人格读不到    → 返回空字符串 → 她变成"没有设定的 AI"
```

复盘结论：**根因不是缺 pipeline，而是这条链路寄生在 7 个不受控的外部契约上。**
任何一处随 AstrBot / LivingMemory / Python 升级而变化，hub 都会静默降级。

### 七个外部契约

| # | 契约 | 用途 | 失效表现 |
|---|---|---|---|
| 1 | AstrBot `data_v4.db` 的 `personas` 表 | 读人格 | 人格为空，她"不是她" |
| 2 | AstrBot session 格式 `一号:FriendMessage:xxx` | 决定 `write_scope` | **写进错误的域，记忆永远召不回** |
| 3 | AstrBot `cmd_config.json` | 取上游 API Key | 上游 Key 读不到，服务不可用 |
| 4 | LivingMemory `conversations.db` | QQ 归档同步 | 同步失败或漏数据 |
| 5 | LivingMemory 外部 API | 写记忆 / 召回 | 写不进、召不回 |
| 6 | LivingMemory 插件源码与 `livingmemory.db` | 原子补丁 / 回填 / 清理 | 插件升级覆盖补丁；schema 变 → 操作坏库 |
| 7 | Python 运行时（AstrBot 自带 venv） | 运行 sidecar | 依赖缺失，服务起不来 |

只有 #5 算公开契约，其余六个都是内部实现——这是当前最大的维护风险。

---

## 决定

### 1. 所有外部访问收进两个适配器

```
AstrBotAdapter      → 契约 1、2、3
LivingMemoryAdapter → 契约 4、5、6
```

- 正常运行路径**不直接读写 LM 数据库**
- `backfill` / `selftest cleanup` 改为离线维护命令
- 每次访问返回 `ContractResult { ok, source, version, sha256, error }`

### 2. 启动时做版本握手，按三级严重度处理

```python
CompatReport = {
    'astrbot': { 'personas_table': ok, 'system_prompt_column': ok, 'persona_id_row': ok },
    'livingmemory': { 'plugin_version': '2.14.2', 'schema_version': 3, 'external_api': ok },
    'session_format': { 'value': '一号:FriendMessage:41328808', 'matches_scope': True },
}
```

**不是"任何一项失败就拒绝启动"**——LM 与 AstrBot 常常比 hub 晚启动，
一律拒绝会让 hub 直接不可用，比静默降级更糟。

| 级别 | 条件 | 行为 |
|---|---|---|
| **FATAL** | 上游 Key/Base 缺失、端口占用、config 不可读、archive 迁移失败 | 拒绝启动 + 状态页给原因 |
| **DEGRADED** | `personas` 表/列/行缺失、LM 不在线、`write_scope` 无法验证、补丁缺失、QQ 源缺失 | **启动 + 红条 + 后台重试握手**，尽量保住聊天 |
| **WARN** | 知识库不可用、同步滞后、死信 > 0 | 启动 + 黄条 |

只有 FATAL 拒绝启动。其余进降级模式，且必须在 **红条 / `/health` / 日志** 三处显式可见。

握手不是一次性的：hub 可能连续运行几天，期间 AstrBot / LM 原地升级，
启动时的 `ok=True` 就不再作数。

**运行时也要探测（CompatMonitor）**：

- 启动时 + 每 5 分钟（或 adapter 连续报错时立即）重探
- `/health` 增加 `compat_checked_at` / `compat_stale`
- 运行中 `ok` 变 `fail` → 立即转 DEGRADED + 红条 + 暂停写回
- 不兼容的版本不重试；暂时不可用的 60 秒重试

**还要区分两种失败**：

| 类型 | 例子 | 处理 |
|---|---|---|
| 不兼容 | schema 改了、表没了 | DEGRADED 或 FATAL，不重试 |
| 暂时不可用 | LM 进程还没起来 | DEGRADED，60 秒后重试握手 |

### 3. 人格是 P0，优先于记忆

**理由**：记忆坏了是"她不知道"；人格坏了是"她不是她"。

- `personas` 表 / `system_prompt` 列 / `persona_id` 行，缺任一项 → `ok=False`
- `build_messages` 不再静默 `return messages`，改为带降级标记继续

**三级人格来源**（优先用能用的最好的）：

| 顺序 | 来源 | 条件 | 界面 |
|---|---|---|---|
| 1 | `astrbot_db` | 正常读到且非空 | 绿 |
| 2 | `lkg`（Last Known Good） | 读到过、暂时读不到 | **黄条**「人格暂用缓存」 |
| 3 | `persona_fallback.txt` 包内精简版 | 从来没成功读过 | **红条**「人设未加载」 |
| 4 | 代码内置最小人格常量 | fallback 文件也缺失 | **红条**「人设兜底」 |

**绝对不允许静默返回原消息。** 四层全空时返回内置常量并标 `degraded=True`，
由界面对用户明示「她的设定没加载」。

边界情况必须覆盖：

- 行存在但 `system_prompt = ''`（空表/空内容）→ 同样走降级，不能当成"读到了"
- 文件存在但内容为空 → 视为缺失

- LKG 落盘：`persona.lkg.json`，含 `text / sha256 / loaded_at / persona_id`
- 一次 DB 抖动只会掉到 LKG，不会直接变成精简版
- LKG 超过 24 小时未更新 → 黄条升红条（避免缓存用一辈子）
- LKG 文件与 persona 同源，含私密内容，放 %APPDATA% 且不导出
- 包内补 `persona_fallback.txt`：**同角色精简版（3–5 条核心），不是通用助手**
- `/health` 增加：`persona_ok / persona_source / persona_stale / persona_chars / persona_sha256 / persona_loaded_at`

### 4. `write_scope` 校验提前到 1b

这是七条契约里第 2 条：**写错域，记忆永远召不回**。属于连通性 P0，不是质量问题。

1b 就做：

- 启动时解析 `write_scope` 的 `platform:message_type:target` 格式
- 用 LM 的 session 列表或 `conversations.db` 验证目标存在
- 验证不了 → DEGRADED + **暂停写回**（宁可这轮不记，也别写进死域）
- 五期只做"召回时按域过滤/去重"，不再负责"写的时候别写错"

### 5. 插件补丁要有负责人（PatchManager，1b）

事故 #4（补丁丢失无提示）会在一期做完后复发，除非有专门机制：

- 识别插件版本 + 文件哈希 + 锚点
- 应用 / 校验 / 回滚
- 补丁丢失 → DEGRADED + 红条
- 插件升级后**自动重试应用**，而不是等用户点「立即修复」
- **自动应用有版本门**：只对「已知支持的插件版本 + 锚点哈希匹配」自动改
- 未知版本 → DEGRADED + 「需人工确认」，**不自动改源码**（防止插错位置）

### 6. 直写数据库限定在维护模式

`backfill_atoms.py` 与 `selftest.cleanup` 会直接写 `livingmemory.db`，必须约束：

- 只在**维护模式**下运行（LM 停止或只读，先备份）
- 界面上不给普通用户一个"清理"按钮直接删库
- 每次直写前校验 schema 版本，不符就拒绝

### 7. 版本化数据与迁移

- `schema_version` 表 + 有序迁移列表
- 迁移必须在监听端口前跑完；幂等、可备份、可回滚
- 用 v0.4.7 的真实库做 fixture 测试
- `archive.db` 开 WAL；首次同步分批提交

### 8. 写入改为 outbox，而不是 daemon 线程

```
聊天线程 → 入队（pending） → worker 认领 → sending → written
                                    ↓ 写入成功但未索引
                              index_pending（最多等 120 秒）
                                    ↓ 仍未检索到
                              index_failed（可重试，不计入死信）

失败分支：sending → failed → 重试 → dead（超次数）
```

- 带 `trace_id` / `attempts` / `next_retry_at`
- 写入后验证可检索：`written` 之后进 `index_pending`，超时转 `index_failed` 并重试
- 提炼失败也落记录并重试（现在只打日志）

### 9. 排期与验收

| 阶段 | 内容 | 工期 | 验收 |
|---|---|---|---|
| **1a** | `contracts.py` + `AstrBotAdapter`(人格) + 三级严重度 + 四层兜底 + LKG(DPAPI) + 单测 + **最小 CI（run_tests.ps1）** | 0.5–1 天 | 六种场景全过：改名 / 空表 / `system_prompt=` / DB 锁 / fallback 缺失 / LKG 过期 |
| **1b** | `LivingMemoryAdapter` + `schema_version` + 迁移 + **scope 校验** + **PatchManager** + 维护模式边界 | 1–1.5 天 | 老库可升级可回退；scope 不匹配时暂停写回 |
| **二期** | outbox + 崩溃恢复 | 2 天 | 发送中杀进程 → 重启自动补写，不丢不重 |
| **三期** | E2E 契约测试（假 AstrBot / LM / DeepSeek）+ CI gate | 1–2 天 | 一条消息跑通全链路，故障注入全过 |
| **四期** | 可观测（结构化事件、状态页"卡在哪层"） | 1 天 | 任意失败能指出层级 |
| **五期** | 质量（去重、作用域过滤、重要度重做） | 3–4 天 | 泛问命中率、去重率、重要度分布 |

合计约 9–11 天。

## 备选方案

| 方案 | 为什么不选 |
|---|---|
| **只做可观测**（原计划一期） | 可观测是事后：坏了更快知道，不能升级前判断 |
| **全量重写** | 现有模块划分（config/upstream/memory/knowledge/prompt/persona）合理，重写会丢掉踩过的坑 |
| **不让 hub 碰数据库，只走 API** | LM 外部 API 不支持删除与原子查询，回填/清理做不到 |
| **通用助手兜底人格** | 等于换了个角色，比报错更让用户困惑 |
| **保持 daemon 线程写入** | 进程崩溃即丢；合并成一个函数也解决不了 |

## 后果

**正面**

- 升级 AstrBot / LM 时，启动就能判断兼容性，不再静默降级
- 人格失效会"喊出来"，不会被误认为"她今天心情不好"
- 写入变成可恢复状态机，进程崩溃不丢记忆
- 每次提交有回归网，不必"手测 + 当天热修"

**负面 / 代价**

- 一期 2–3 天功能冻结
- 新增两个适配器文件，代码量增加约 400 行
- 版本不兼容时**按三级严重度处理**：只有 FATAL 拒绝启动；DEGRADED 会红条运行并后台重试握手
- 维护者需要同步维护兼容矩阵

**风险**

- 适配器可能过度抽象：只包实际用到的 6 个方法，不做通用框架
- 迁移 runner 写错可能坏库：所有迁移前强制备份，且 fixture 测试覆盖

---

## 非目标

- 不换框架（Electron + Python 够用）
- 不重写检索（LM 的混合检索强于自研）
- 不做多用户 / 权限
- 不做自动更新
- 不把插件补丁上游化（上游不接受就不强推，维持本地补丁 + 自检）

| 阶段 | 回滚方式 |
|---|---|
| 1a | 适配器是新增文件，删掉即回退；`persona.py` 保留原函数名 |
| 1b | 迁移前自动备份 `archive.db`；`schema_version` 降级脚本 |

| 三期 | 测试失败不阻塞运行，只阻塞发布 |

## 里程碑：v1.0.0

本 ADR 的全部内容合并为 **v1.0.0** 一个大版本，不拆分到 0.4.x / 0.5.x。

### 版本策略

| 版本 | 含义 |
|---|---|
| v0.4.7 | 当前版本（冻结功能，只修紧急缺陷） |
| v0.4.x | 只接受阻断性修复，不再加功能 |
| **v1.0.0** | 契约层 + 迁移 + outbox + E2E + 可观测 + 质量，全部完成 |

### 为什么合并成一个大版本

1. **六段互相依赖**：outbox 没做完，E2E 测不了崩溃恢复；适配器没做完，迁移无处落地
2. **中途发布反而危险**：契约改到一半发版，用户会遇到"新旧混用"的中间态
3. **v1.0 是一个承诺**：从"能跑"到"能长期维护"，值得一个完整版本号

### 发布门槛（全部满足才发 v1.0.0）

| # | 门槛 | 验收方式 |
|---|---|---|
| 1 | 人格缺失会报错并红条 | 改 `personas` 表名测试 |
| 2 | 老库可迁移、可回滚 | v0.4.7 真实库 fixture |
| 3 | 崩溃不丢记忆 | 强杀进程后自动补写 |
| 4 | 全链路自动测试通过 | 假 AstrBot/LM/DeepSeek |
| 5 | 状态页能指出失败层 | 注入故障观察 |
| 6 | 质量指标达标 | 重要度分布、去重率、泛问命中 |
| 7 | 兼容矩阵写入 README | AstrBot × LM × Python × hub |

### 施工方式

- 按 1a → 1b → 二期 → 三期 → 四期 → 五期 顺序
- 每段完成即合并到 `main`，但不发版
- 全部完成后一次性发 v1.0.0
- 中途用户想用，仍用 v0.4.7
